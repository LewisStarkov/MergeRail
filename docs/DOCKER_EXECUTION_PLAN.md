# Docker-исполнение с ограничением ресурсов и синхронизацией через Git

Статус: исходный план и расширенная дорожная карта. Реализованный режим и его
ограничения описаны в [DOCKER_EXECUTION.md](DOCKER_EXECUTION.md).

Проверка 2026-09-28: этап A начат, gate не пройден. Результаты и воспроизводимый
прототип: [DOCKER_EXECUTION_STAGE_A.md](DOCKER_EXECUTION_STAGE_A.md).
Этот результат относится к прототипу на 2026-09-28. Поддержка платформ ниже
остаётся целевой и не заменяет текущую матрицу поддержки.

## Цель

Запускать агентов, проверки и команды проекта в Docker, чтобы они не могли напрямую
изменять устройство за пределами выделенной среды. Сохранить работу с локальным
репозиторием и не держать тяжёлое окружение включённым без необходимости.

Поддерживаемые хосты: macOS, Linux и Windows с Docker в режиме Linux containers.
Среда проекта внутри контейнера — Linux. Нативные macOS/iOS/Windows-сборки в MVP
не поддерживаются; отсутствие поддержки не должно приводить к запуску на хосте.

## Основные решения

- Доверенный контроллер MergeRail работает на хосте: очередь, интерфейсы, политика,
  управление Docker, импорт результата и доставка.
- Весь недоверенный код выполняется в контейнерах: агенты, внешние драйверы,
  диагностические вызовы этих драйверов, установка зависимостей, тесты и приложение.
- Рабочая копия имеет собственную `.git`. Основной репозиторий и его Git metadata
  никогда не подключаются к контейнеру через bind mount.
- Синхронизация выполняется через локальные Git bundles; GitHub и Git-сервер не нужны.
- По умолчанию одновременно работает одна тяжёлая стадия на весь экземпляр MergeRail.
- Между задачами сохраняются данные и кэши, но не работающие процессы.
- Если защиту или обязательные лимиты невозможно применить, выполнение останавливается.
  Автоматического перехода к локальному исполнению нет.

## 1. Граница доверия

Контейнеру запрещены privileged-режим, Docker socket, host PID/network namespaces,
доступ к устройствам, домашней папке, SSH-agent, хранилищу задач и секретам интерфейсов.
Процессы работают от непривилегированного пользователя, с `no-new-privileges`,
сброшенными capabilities, стандартным seccomp-профилем и read-only системным слоем.
Запись разрешена только в отдельные рабочие данные и ограниченные временные каталоги.

Политика исполнения фиксируется контроллером перед задачей. Файлы из рабочей копии,
включая изменённый `mergerail.toml`, не могут разрешать дополнительные mounts,
сеть, привилегии или увеличение лимитов. Обновление оператором применяется к следующей
задаче. Параметр агента `permission` не управляет внешней Docker-изоляцией.

Контейнеризация не защищает от всех уязвимостей ядра/runtime. Кроме того, разрешённая
передача исходников AI-провайдеру остаётся частью работы агента. Не обещать абсолютную
изоляцию или отсутствие передачи данных. Требования к минимальным версиям runtime,
обновлениям образов и поддерживаемым платформам фиксируются после проверки прототипа.
Причины ограничений описаны в [Docker security](https://docs.docker.com/engine/security/).

## 2. Бюджет ресурсов

Начальный профиль `eco` — проектируемые значения, которые нужно подтвердить замерами:

| Ресурс | Начальная настройка | Поведение |
| --- | --- | --- |
| Активные задачи | 1 | Общая очередь для репозиториев этого пользователя |
| CPU тяжёлой стадии | 1 CPU | Жёсткая квота, а не только приоритет |
| RAM тяжёлой стадии | 2 GiB | При OOM задача останавливается с диагностикой |
| Swap контейнера | 0 | `memory-swap` равен `memory`, если runtime это поддерживает |
| Процессы | 128 | Проверяемый PID limit |
| `/tmp` | 128 MiB | Ограниченный tmpfs, учитывается в RAM |
| Логи задачи | 20 MiB | Ограничение потока и ротация Docker-логов |
| Рабочие данные | 4 GiB | Требуется реально обеспечиваемая квота |
| Общий кэш MergeRail | 4 GiB | Очистка LRU с защитой используемых объектов |
| Транспортный bundle | 256 MiB | Ограничение при приёме, до разбора Git |
| Вспомогательный сетевой шлюз | 0.1 CPU / 128 MiB | Только во время стадии с сетью |
| Простой | 60 секунд | Остановить все контейнеры задачи и шлюз |

Значения можно изменить оператору. Не повышать их автоматически после ошибки.
Большой репозиторий или тяжёлая сборка должны получать понятное сообщение о конкретном
лимите, а не бесконечные повторные попытки.

Общие правила экономии:

- Fixer, проверки и reviewer выполняются последовательно. У них разные права и
  процессы, но общие неизменяемые слои образов.
- Один контейнер стадии можно использовать для нескольких команд, пока стадия активна.
  Не держать постоянный `sleep infinity` между задачами.
- Приложение из `Supervisor` по умолчанию выключено. Если оператор его включил,
  в `eco` оно останавливается перед тяжёлой стадией; постоянный параллельный запуск
  требует отдельного бюджета. UI явно показывает эту паузу.
- Сохранять backend session IDs и допустимые файлы сессии в пределах одной задачи.
  Остановка контейнера не означает обязательную потерю сессии; совместимость проверять
  для каждого backend. Между независимыми задачами сессии не переносить.
- Не создавать образ на каждый раунд. Образы закрепить по digest; предоставлять
  отдельные минимальные Python/Node-профили и архитектуры arm64/amd64.
- Не включать эмуляцию другой архитектуры автоматически.
- Не запускать модели локально: контейнер содержит CLI и инструменты проекта.
- Установку зависимостей запускать только при изменении lockfile/образа/архитектуры.
  Download cache отделить от установленного окружения; кэш не считать доверенным.
  Проверки и reviewer не должны переиспользовать исполняемое окружение, изменённое fixer.
- Кэш разделять по репозиторию, lockfile, образу и архитектуре. Нельзя давать одной
  задаче возможность отравить общий исполняемый кэш другой задачи.
- Между запусками не сканировать дерево файлов и не опрашивать Docker каждую секунду.
  Метрики собирать только при активной работе, например раз в 5 секунд.
- Между несколькими процессами MergeRail использовать общий пользовательский lease
  на ресурсный слот. В него не входят чужие контейнеры пользователя.

Docker не ограничивает контейнеры по CPU/RAM по умолчанию; лимиты задаются явно.
Семантику swap и проверку поддержки взять из
[официальной документации](https://docs.docker.com/engine/containers/resource_constraints/).

### Расход Docker Desktop

Лимит контейнера не равен полному расходу Docker Desktop: остаются VM, daemon,
кэш файловой системы и вспомогательные процессы. Диагностика должна различать эти
показатели, показывать бюджет Docker VM и учитывать другие контейнеры.

После остановки контейнеров не мешать Resource Saver переходить в простой.
На Windows/WSL его поведение отличается: для возврата памяти важен также
`autoMemoryReclaim`. Не менять глобальные настройки Docker/WSL без отдельного
действия пользователя и не останавливать чужие контейнеры.
См. [Resource Saver](https://docs.docker.com/desktop/use-desktop/resource-saver/).

### Дисковая квота — обязательная проверка прототипа

Обычный named volume не является универсальным механизмом жёсткой квоты.
`storage-opt size` тоже нельзя считать переносимым ограничением всех подключённых
томов. Проверка размера раз в несколько секунд и остановка при заполнении — лишь
дополнительный контроль, а не защита от быстрого заполнения диска.

До основного внедрения проверить на Docker Engine и Docker Desktop способ размещения
рабочих данных и кэшей в хранилище с обеспечиваемой квотой. Ограничить также распаковку
Git-объектов и сборочные данные. Если переносимый вариант недоступен, зафиксировать
поддерживаемые конфигурации; защищённый режим на остальных не запускать. Нельзя ради
квоты выдавать недоверенному контейнеру privileged-доступ.

Образы и build cache учитывать отдельно от рабочих томов. Перед pull/build проверять
свободное место и бюджет; не запускать автоматическую неограниченную сборку пользовательских
Dockerfile. В MVP использовать доверенные готовые образы. Удалять только ресурсы,
принадлежащие MergeRail; не выполнять глобальный `docker system prune`.

## 3. Синхронизация с локальным репозиторием

Синхронизируем зафиксированные Git-снимки на границах стадий. Живой двусторонней
синхронизации файлов и общей writable-папки нет: это сохраняет границу безопасности
и уменьшает фоновую нагрузку.

```text
Локальный base SHA
    → Git bundle
    → отдельный репозиторий в Docker
    → fixer → зафиксированный result SHA
    → изолированные проверки → reviewer
    → bundle результата → карантин → локальная ветка задачи
    → интеграционные проверки в Docker → доставка
```

### Передача исходников

1. Контроллер фиксирует `base_sha`, идентификаторы задачи/попытки и выбранную ветку.
2. Из этого коммита создаётся bundle только с нужной историей/refs, без `--all`.
   Секреты, уже закоммиченные в выбранной истории, не исчезают автоматически: это
   ограничение нужно явно указать пользователю.
3. Bundle передаётся потоком без подключения локального репозитория к контейнеру.
   Внутри создаётся независимый репозиторий без Git alternates, host paths и hooks.
4. При повторной передаче использовать incremental bundle только после подтверждения
   prerequisite-коммитов на принимающей стороне. При несовпадении пересоздать копию
   из зафиксированного base, не менять пользовательскую ветку.
5. `.env`, ignored/untracked-файлы, локальные venv и `node_modules` не копируются.
   Дополнительные входные файлы передаются отдельно по явному allowlist и лимитам.

[Git bundle](https://git-scm.com/docs/git-bundle) поддерживает локальную передачу
объектов и refs, включая инкрементальные пакеты, без постоянно работающего сервера.

### Локальные незакоммиченные изменения

- По умолчанию задача начинается от выбранного коммита, а не от содержимого редактора.
  Показывать пользователю исходный SHA и факт наличия локальных изменений.
- Не выполнять автоматические stash, reset, clean или commit в рабочей папке пользователя.
- Грязная рабочая папка не мешает работе над отдельной копией; она блокирует локальную
  доставку. Результат сохраняется в отдельной ветке.
- Импорт незакоммиченных изменений в задачу оставить следующей версией: это отдельное
  явное действие со снимком и собственным учётом base.

### Возврат результата

1. Остановить процессы, способные менять рабочую копию, и зафиксировать `result_sha`.
   Снимок хранится вне доступа последующих недоверенных стадий.
2. Проверки выполняются в отдельной одноразовой копии снимка без ключей агентов.
   Их побочные изменения не включаются в результат. Reviewer получает тот же SHA
   и исходники read-only, со своим ограниченным временным каталогом.
3. Bundle принимается контроллером в ограниченный карантин. Разбор недоверенных pack
   выполняется изолированно с лимитами RAM, CPU, распакованного размера и времени.
   Проверять prerequisites, целостность объектов, ancestry от base и ожидаемый tip.
4. Не доверять произвольным refs из bundle. Разрешить импорт только ожидаемого SHA
   в назначенную контроллером ветку `mergerail/<task>/a<attempt>`.
5. Проверить дерево на опасные пути, case-insensitive/Windows-коллизии, Git metadata
   aliases и выходящие за пределы проекта symlinks. В MVP не поддерживать submodules
   и Git LFS; обнаруживать их до запуска с понятной причиной.
6. На хосте использовать очищенную конфигурацию Git и фиксированный набор команд;
   исключить hooks, filters, external diff, fsmonitor, неявные helpers и submodule
   recursion. Настройки из контейнера не импортируются. Доставка использует отдельно
   разрешённую оператором конфигурацию remote/auth.
7. Записать в журнал base/result SHA, digest политики/образа и результат проверок.
   Повторный импорт того же результата должен быть идемпотентным.

### Применение на локальной машине

Сохранить существующие режимы `delivery = local | pr | auto`.

- `local`: собрать кандидат слияния с актуальной основной веткой, проверить его
  отдельную копию в Docker и применить только при неизменившихся base SHA, ветке
  и чистом рабочем дереве. Не обходить коллизии с untracked-файлами.
- Если основная ветка сдвинулась, проверять новый кандидат заново. При конфликте
  сохранить ветку результата и диагностировать конфликт; не выполнять force/reset.
- `pr`: push и создание PR выполняет доверенный контроллер с локальными credentials.
  Контейнер не получает эти credentials. Сохранить текущие проверки точного SHA.
- Параллельные операции самого MergeRail сериализовать lease. Перед обновлением
  refs применять compare-and-swap; при конкурентных пользовательских Git-операциях
  завершать доставку без перезаписи их изменений. Проверить гонки checkout отдельно.
- `retry-delivery` использует сохранённый проверенный результат и не запускает fixer.

## 4. Сеть и авторизация

- Для тестов и большинства команд использовать `network=none`.
- Для AI-вызовов и установки зависимостей применять отдельный контролируемый egress.
  Контейнер не имеет прямого выхода в Интернет или сеть устройства; переменной
  `HTTP_PROXY` без сетевого запрета недостаточно.
- Шлюз ограничивает destinations/ports, запрещает private/link-local/metadata адреса,
  проверяет DNS/redirects и не позволяет использовать произвольный CONNECT-туннель.
  Его overhead входит в общий бюджет, после стадии шлюз останавливается.
- Не наследовать окружение хоста целиком. Разрешённые AI credentials передаются
  только агентной стадии; тесты и установка зависимостей их не получают.
- Не монтировать целиком `~/.codex`, `~/.claude`, `~/.config`, keychain или SSH-agent.
  Способы API-key/OAuth авторизации подтвердить для каждого CLI в прототипе.
  Если совместим только конкретный способ, явно ограничить поддержку.
- CLI-обновления и плагины не должны незаметно менять закреплённое окружение.
- Preview-порты приложения включаются отдельно и публикуются только на loopback.

## 5. Изменения в коде

Названия новых модулей предварительные; не вводить общий framework сверх нужд проекта.

| Модуль | Изменение |
| --- | --- |
| `execution/base.py` | Контракт запуска, streaming, stdin, exit code, cancel, lifecycle |
| `execution/docker.py` | Docker CLI без shell-интерполяции, лимиты, labels, cleanup |
| `execution/policy.py` | Проверка mounts, сети, образов, ресурсов и эффективной политики |
| `execution/sync.py` | Bundle transport, карантин, immutable snapshots, импорт refs |
| `backends/process.py`, `backends/claude.py`, `backends/external.py` | Перевести все пути исполнения на executor |
| `backends/codex.py`, `backends/opencode.py`, registry/probes | Пути внутри контейнера, обнаружение CLI внутри образа |
| `checks.py` | Baseline, обычные и интеграционные проверки через executor |
| `supervisor.py` | Изолированный процесс приложения и политика паузы `eco` |
| `runner.py` | Стадии, resource lease, snapshots, recovery и сохранение результата |
| `gitctl.py`, `delivery.py` | Разделить host Git и sandbox Git; импорт и проверяемая доставка |
| `config.py`, `setup.py`, `cli.py` | Валидация конфигурации, preflight, диагностика и миграция |
| `tasks.py`, `audit.py` | Версионируемые execution metadata и идемпотентные стадии |
| `fronts/web.py`, `webui/src/*` | Режим защиты, ресурсные ошибки, исходный/результирующий SHA |

Для MVP использовать установленный Docker CLI; сохранить отсутствие обязательных
Python-зависимостей. Поддержать только локальный Docker context с Linux engine;
удалённые contexts требуют отдельной модели доверия и пока отклоняются.

Хостовый контроллер должен запускаться из установленного доверенного пакета,
а не импортировать свой код из изменяемой агентом рабочей копии. Перечислить и
проверить оставшиеся host subprocess-вызовы, включая Git и служебные обновления.
Пользовательский backend executable с хоста не запускать для проверки версии.

## 6. Конфигурация и диагностика

Предлагаемый интерфейс; указанные ключи пока не реализованы:

```toml
[execution]
backend = "docker"
required = true
profile = "eco"
cpus = 1.0
memory_mib = 2048
pids_limit = 128
idle_stop_seconds = 60
workspace_limit_mib = 4096
cache_limit_mib = 4096

[execution.sync]
mode = "git-bundle"
include_uncommitted = false
max_bundle_mib = 256
```

`mergerail doctor` должен проверять engine/context, архитектуру, доступность образа,
авторизацию, реальные ограничения, квоту, запас диска и возможность остановить всё
дерево процессов. Активная проверка изоляции использует только специально созданные
контрольные файлы. Не выполнять проектные проверки на хосте даже через doctor.

В интерфейсах показывать: фазу, заданный бюджет, OOM/timeout/disk-limit, статус
синхронизации, base/result SHA, наличие результата при ошибке доставки. Не называть
проект защищённым, если preflight не завершён.

Новые установки получают обязательный Docker-режим после его валидации. Существующие
конфигурации проходят явную миграцию; не начинать автоматически установку Docker,
скачивание больших образов или изменение глобальных настроек устройства.

## 7. Отмена, сбои и очистка

- Каждому ресурсу назначить labels владельца, repository ID, task ID и attempt ID.
- Отмена останавливает контейнер целиком, включая фоновые дочерние процессы;
  по истечении grace period применяется kill. Не ограничиваться остановкой Docker CLI.
- После остановки сохранить доступные изменения отдельным ограниченным recovery-шагом
  без сети/секретов. Если Docker недоступен, отметить результат как не сохранённый,
  удержать volume и не сообщать об успешном восстановлении.
- При рестарте сверять журнал с реальными Docker-ресурсами до повторного запуска.
  Не допускать двух исполнителей одной попытки или повторной доставки.
- Непроверенные recovery-коммиты помечаются явно и не доставляются автоматически.
- Удаление временных ресурсов выполняется после подтверждённого сохранения результата.
  Не удалять рабочие данные активных и восстанавливаемых задач ради LRU-очистки.

## 9. Проверки и критерии готовности

### Безопасность и сохранность данных

- Агент, тест и их дочерние процессы не могут изменить контрольный файл вне среды
  через абсолютный путь, `..`, symlink, hook или фоновый процесс.
- Docker socket, локальные службы, credentials контроллера и домашняя папка недоступны.
- Изменение конфигурации в задаче не ослабляет runtime-политику.
- Повреждённый/слишком большой bundle, чужие refs, недостающие prerequisites,
  path collisions и расходящиеся SHA отклоняются до доставки.
- Проверки не могут подменить доставляемый снимок; одобрение связано с точным SHA.
- Dirty tree, конфликт и движение base не приводят к потере локальных файлов.
- Перезапуск, OOM, disk-limit, отмена и недоступный Docker сохраняют честный статус
  и позволяют повторить только необходимую стадию.

### Ресурсы и скорость

- При пустой очереди через 60 секунд у MergeRail нет работающих контейнеров,
  сетевых шлюзов, watchers и процессов опроса Docker.
- В `eco` одновременно активна максимум одна тяжёлая стадия; её лимиты подтверждены
  нагрузочным тестом. Учитываются pack/unpack, установка зависимостей и helpers.
- Искусственное заполнение ограниченного хранилища завершается внутри квоты и
  не заполняет диск устройства. Наблюдение за размером не заменяет этот тест.
- Неизменные образ/lockfile не вызывают повторного pull/install; источник кэша проверен.
- На повторной Git-синхронизации передаются только отсутствующие объекты, если
  подтверждены prerequisites. Размер bundle и время передачи записываются в метрики.
- Сравнить native baseline, cold Docker, warm Docker и idle для одного проекта:
  wall time, CPU time, peak RAM, Docker VM RAM, записанные/переданные байты.
- Цель для warm оркестрации: не более 5 секунд overhead на короткую задачу
  без AI-задержки, установки зависимостей и пробуждения Docker VM. Это целевой
  показатель для замера, не обещание до измерений; результаты записать по платформам.
- Не обещать возврат всей RAM Docker Desktop сразу после остановки контейнеров.

Использовать unit-тесты для контрактов и настоящие Docker integration tests для
изоляции. Проверка сформированных CLI-флагов сама по себе не доказывает защиту.
Опасные сценарии воспроизводить только на тестовых файлах и в ограниченной среде.

## 10. Что остаётся за пределами MVP

- Live sync незакоммиченных файлов редактора в обе стороны.
- Нативные сборки macOS/iOS/Windows, GPU и Docker-in-Docker.
- Неограниченные пользовательские Dockerfile и произвольные mounts.
- Удалённый Docker, распределённые исполнители, несколько тяжёлых задач одновременно.
- Автоматическое изменение глобальных ресурсов Docker Desktop/WSL.
- Git submodules и LFS до отдельной реализации передачи и проверки данных.

MVP готов, когда задача проходит полный цикл в Docker, проверенный результат
появляется в локальном Git без потери пользовательских изменений, а в простое
MergeRail не держит вычислительную среду работающей.
